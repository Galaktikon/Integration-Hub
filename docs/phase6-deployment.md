# Phase 6 deployment and demo runbook

This runbook is for the agreed architecture: one always-on Render web service runs the API, sync worker, and scheduler; a second Render web service hosts synthetic Commerce and ERP APIs; a Render static site hosts the dashboard; Neon PostgreSQL holds durable state. The repository does not contain a public demo URL or production secrets. The public demo is complete only after the hosted checks below pass.

## 1. Accounts and repository

1. Create a [Neon project](https://neon.com/docs/get-started/signing-up) with PostgreSQL 17 if offered. Select a region near the Render region you will choose. Keep the project owner connection details private.
2. Create a [Render account](https://render.com/docs/infrastructure-as-code) and connect the Git repository. This deployment uses two paid, always-on `0.5c-512mb` web services. Review the current plan costs before creating them. The dashboard is a static site.
3. Keep `render.yaml` on the branch you deploy. The Blueprint has automatic deploys disabled so migrations, API, simulator, and dashboard can be released in order. Create a Blueprint from this repository in Render after completing the database preparation below.
4. Use only synthetic orders. Do not connect real vendor systems or reuse the local development keys.

## 2. Prepare Neon

Use one Neon database with separate `hub` and `demo` schemas. Use the project owner or another migration-capable role only for migrations. Create separate login roles `hub_runtime` and `demo_runtime` **with SQL**, not with the Neon Console's **Add role** button: Console-created roles inherit `neon_superuser`, whereas SQL-created roles can be granted only the permissions below. Run `CREATE ROLE hub_runtime LOGIN;` and `CREATE ROLE demo_runtime LOGIN;` as the project owner, then set high-entropy passwords using interactive `psql` commands `\password hub_runtime` and `\password demo_runtime` so the passwords are not pasted into SQL history. The runtime roles must not own tables or have schema creation privileges. [Neon role guidance](https://neon.com/docs/manage/roles).

From the repository root on a machine with Docker, run the migration helper:

```powershell
.\scripts\neon-migrate.ps1
```

The helper prompts privately for the hub and simulator migration connection strings, builds both images, runs both EF Core migrations, then clears the temporary environment variables. Use the **direct**, non-pooled Neon host and the migration role for each prompt. Use Npgsql key/value connection strings, not PostgreSQL URL syntax. Include `SSL Mode=Require` and a bounded pool, for example `Host=<direct-neon-host>;Port=5432;Database=<database>;Username=<migration-user>;Password=<secret>;SSL Mode=Require;Maximum Pool Size=10`. Do not paste a real connection string into a tracked file or command history.

The simulator requires two distinct key values even during its migration command; the helper uses placeholders only for that command, and they never become hosted credentials.

In Neon SQL Editor, connected as the migration owner, grant the runtime roles access after migrations:

```sql
GRANT USAGE ON SCHEMA hub TO hub_runtime;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA hub TO hub_runtime;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA hub TO hub_runtime;
GRANT USAGE ON SCHEMA demo TO demo_runtime;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA demo TO demo_runtime;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA demo TO demo_runtime;
```

Reapply the table and sequence grants after future migrations. `hub_runtime` and `demo_runtime` must each be able to read their schema's `__EFMigrationsHistory` table for readiness checks. Use separate Npgsql connection strings with the runtime role passwords in Render. A pooled Neon host is suitable for normal API traffic; keep migrations on the direct host. Neon requires TLS, and its pooled host is identified by `-pooler` in the hostname. [Neon connection guidance](https://neon.com/docs/manage/endpoints/).

## 3. Configure the Render Blueprint

Create a Blueprint using [render.yaml](../render.yaml). Before the first deployment, fill each `sync: false` variable in Render:

| Service | Variable | Value |
| --- | --- | --- |
| API | `ConnectionStrings__Hub` | Neon runtime connection string for `hub_runtime`, with TLS and a bounded pool |
| API | `Security__AdminUsername` | A new admin username |
| API | `Security__AdminPasswordHash` | PBKDF2 hash generated by `scripts/new-admin-credentials.ps1` |
| API | `Security__AllowedConnectorHosts` | Exact public hostname of the Render simulator, without scheme or path |
| API | `Security__FrontendOrigin` | Exact HTTPS origin of the Render dashboard, without a trailing slash |
| API | `Demo__BaseUrl` | Exact HTTPS origin of the Render simulator, without a trailing slash |
| Simulator | `ConnectionStrings__Demo` | Neon runtime connection string for `demo_runtime`, with TLS and a bounded pool |
| Dashboard | `VITE_API_BASE_URL` | Exact HTTPS origin of the Render API, without a trailing slash |

Run `scripts/new-admin-credentials.ps1` locally, enter a new password of at least 16 characters, and copy only the resulting password hash to `Security__AdminPasswordHash`. Store the password in your password manager. The Blueprint generates and retains separate 32-byte encryption and token-signing keys. **Never replace `Security__EncryptionKey` after connectors have been saved** unless you also rotate and re-encrypt their secrets. The simulator's API and admin keys are generated separately by Render and referenced by the API service; neither belongs in the static site.

Render's `ASPNETCORE_URLS` setting binds the two .NET services to port 10000. Both health checks use database connectivity and migration state. Render terminates public HTTPS; the API allows only the configured dashboard origin through CORS. The dashboard build embeds `VITE_API_BASE_URL`, so a URL change requires a new static-site build. Render Blueprint `sync: false` values are prompted for on initial creation and must be changed manually later. If Render assigns a hostname different from the one you anticipated, correct `Security__AllowedConnectorHosts`, `Security__FrontendOrigin`, `Demo__BaseUrl`, or `VITE_API_BASE_URL` as applicable and redeploy the affected service. [Render Blueprint reference](https://render.com/docs/blueprint-spec/).

Deploy simulator, API, then dashboard after the migrations and environment variables are in place. Confirm both readiness URLs return `{"status":"ready"}` before testing the dashboard:

```text
https://<simulator-host>/health/ready
https://<api-host>/api/v1/health/ready
```

## 4. Seed and configure the synthetic demo

The simulator's admin routes require `Demo__AdminKey`. In a private terminal, call `POST https://<simulator-host>/__admin/seed` with `X-Api-Key: <admin-key>`. It idempotently creates 125 synthetic Commerce orders. Do not place the admin key in the browser or static site.

Sign in to the dashboard with the new admin credentials. Add two enabled REST connectors:

- **Demo Commerce**, role **Source**, base URL `https://<simulator-host>/commerce`.
- **Demo ERP**, role **Destination**, base URL `https://<simulator-host>/erp`.

For both connectors, enter the simulator's generated `Demo__ApiKey` from Render, set page size to 100 and timeout to 15 seconds, then use **Test**. The key is encrypted before storage and is never returned by the API. Create an enabled integration with the default four mappings, then run it. Confirm 125 fetched records and 125 ERP rows created on the first clean run. A later run should report unchanged rows rather than duplicates.

## 5. Demonstrate recovery

1. In **Integrations**, select the demo flow, click **One 503**, then **Run now**. In **Run history**, show the run's persisted retry and eventual completion. The hosted fault proxy is protected by administrator login and accepts only bounded source 503 faults.
2. Click **Outage for retry demo**, start a new run, wait until the source attempt budget is exhausted, then use **Retry run** when the API allows it. Show that the same run continues from its persisted checkpoint.
3. For restart recovery, start a run and redeploy or restart only the combined API/worker service. The worker resumes after its lease expires. Use the record and attempt history to show the continuation. Avoid restarting during an external write solely for a public interview; the scripted local test covers that edge case reproducibly.
4. Record the run ID, status, counts, attempt history, and ERP row count as evidence. Do not claim a recovery scenario passed unless its observed result matches the expected outcome.

The simulator supports a protected reset of **synthetic destination rows and fault state**. Disable schedules and wait for active runs to finish first. Then send `POST https://<simulator-host>/__admin/reset` with the simulator admin key and `X-Confirm-Reset: reset-synthetic-demo`. It retains or reseeds the 125 source orders. Existing hub run history and integration definitions remain; create a new integration or use a fresh Neon branch for a fully clean presentation. This endpoint is not exposed through the dashboard.

## 6. Verify and release

From a clean checkout, run local Compose, seed, and the test commands in the [README](../README.md). Browser smoke tests live in `frontend/admin-dashboard/e2e`:

```powershell
cd frontend/admin-dashboard
npm ci
npx playwright install chromium
$env:E2E_ADMIN_PASSWORD = '<local-demo-password>'
npm run test:e2e
```

Set `E2E_MUTATE=1` only against a disposable, seeded local environment to run the create-and-launch test. Against the hosted site, set `E2E_BASE_URL`, `E2E_ADMIN_USERNAME`, and `E2E_ADMIN_PASSWORD` and leave `E2E_MUTATE` unset for a read-only sign-in/navigation smoke. CI runs .NET regression tests and both local browser smoke tests. It must be green on the deployed commit before calling the demo complete.

Review Render logs by correlation ID (`X-Correlation-ID` response header), run ID, and lease generation. The API emits JSON logs outside Development and instruments HTTP requests, durations, run claims, terminal statuses, and run duration with a .NET `Meter`. Authenticated `GET /api/v1/metrics` exposes aggregate run statuses, retry events, and uncertain attempts for the demo; the Meter can be connected to an exporter later. Liveness checks the process; readiness checks Neon connectivity and migration state. Neither health endpoint requires an admin token.

## Known limits and trade-offs

- The API, sync worker, and scheduler share one process by design. The database lease and fencing generation handle overlapping deploy instances and restart continuation. A sleeping/free web instance would pause scheduled work, so an always-on Render plan is required.
- The hosted demo uses synthetic REST contracts, not real vendor OAuth or webhooks. The simulator snapshot token is intentionally stable for the demo and does not prove behavior against an arbitrary vendor API.
- The admin account is a single operator identity with an eight-hour bearer token kept in browser memory. There is no multi-user RBAC, audit export, or self-service password reset.
- The fault proxy demonstrates bounded source 503 failures. The lost-response and stale-worker fencing cases are covered by local integration tests and `scripts/phase4-recovery.ps1` rather than exposed as public buttons.
- Neon compute may remain active because the worker and scheduler poll PostgreSQL. Review Neon usage after deployment.
- Production smoke is read-only by default. It verifies sign-in and navigation; manually confirm hosted failure, retry, reset, and restart behavior before sharing a public URL.
